# Выявленные противоречия и способы их решения

---

# Данный артефакт был существенно изменён для сохранения коммерческой тайны и служит только для демонстрации структуры аналитических решений.

---

## Обзор

В рамках анализа системы управления маркировкой товаров выявлены критические противоречия между требованиями регулятора, физическими условиями склада и текущими бизнес-процессами.

**Ключевая проблема:** На складе одновременно действуют несколько взаимоисключающих требования. Их нельзя исполнить одновременно физически. Текущие процессы обеспечивают отгрузку, но создают риски несоответствия требованиям регулятора.

---

## 1. Три взаимоисключающих сценария

**Статус:** Критическая серьёзность

**Суть противоречия:**

Существуют три сценария работы, которые по отдельности работают, но вместе создают неразрешимый конфликт:

### Сценарий 1 — требование регулятора
- Каждое изделие сканируется с физического стикера при отгрузке
- Изделие уходит клиенту со стикером кода маркировки
- Код выводится из оборота в момент отгрузки
- Хранить полные коды на стороне владельца ограничено по времени
- Повторная печать стикера возможна в течение ограниченного периода

### Сценарий 2 — ответственное хранение
- Клиент не может ждать получения кодов и подтверждения от регулятора
- Отгрузка может проводиться без немедленной реализации в учётной системе
- Реализация проводится с задержкой, когда товар встанет на баланс
- Документы с кодами уходят клиенту с задержкой по ЭДО

### Сценарий 3 — отгрузка на внешнюю площадку
- Персонал работает ограниченное количество часов и не может ожидать коды
- Отгрузка может проводиться без немедленной реализации в учётной системе
- Клиент может забрать товар — коды на изделиях могут стать неактуальными
- Клиент может не забрать товар — изделие остаётся на внешней площадке в неопределённом статусе
- Реализация проводится постфактум, документы по ЭДО с задержкой

**Почему сценарии несовместимы:**

| Требование | Сценарий 1 (регулятор) | Сценарий 2 (ОХ) | Сценарий 3 (внешняя площадка) |
|-----------|------------------------|-----------------|------------------------------|
| Стикер на изделии | Изделие уезжает со стикером | Изделие уезжает без стикера | Изделие уезжает без стикера |
| Сканирование в момент отгрузки | Да | Отгрузка сейчас, оформление потом | Отгрузка сейчас, оформление потом, статус неизвестен |
| Код привязан к физическому изделию | Да | Код из документа в учётной системе | Код из документа в учётной системе |
| Хранить коды ограничено | Да | Быстрый доступ к кодам нужен | Быстрый доступ нужен + риск зависшего статуса |
| Вывод из оборота при отгрузке | Да | Вывод постфактум | Вывод постфактум, если клиент забрал товар |

**Сценарии 2 и 3 — наиболее загруженные и фактически используемые.** Они основаны на схемах отгрузки без немедленной реализации, которые работают, но создают риски несоответствия требованиям.

**Рекомендация:** Легализовать схемы ответственного хранения и отгрузки на внешние площадки через согласование с регулятором.

## 2. Физическое разрушение стикеров при хранении

**Статус:** Критическая серьёзность

**Суть противоречия:**

Требование «сканировать с изделия и отдать со стикером» несовместимо с физическими условиями хранения продукции в стопках.

**Почему стикеры разрушаются:**
- При постоянном ручном перекатывании и перекладывании стикеры трутся руками персонала
- Трение о соседние изделия в стопке
- Трение об пол при перекатывании
- Трение о борта и пол при погрузке/транспортировке/выгрузке
- Каждое касание — потенциал повреждения стикера
- Продукция тяжёлая, контакт с поверхностью постоянный

**Сканирование с изделий:**
- Физически невозможно в стопках — это подтверждается практикой инвентаризации
- Именно поэтому ТСД при инвентаризации не используется
- Сканирование возможно только когда все изделия сняты со стопки И стикеры не нарушены

**Рекомендация:** Рассмотреть изменение способа хранения для обеспечения доступа к стикерам, либо легализовать сканирование из документов учётной системы.

## 3. Деградация кодов (накопительный эффект)

**Статус:** Критическая серьёзность

**Суть противоречия:**

С каждой отгрузкой разрыв между системой и реальностью растёт по замкнутому циклу:

```
Код нужен для отгрузки
- на стикере он нечитаем (из-за условий хранения)
- используется "коммерческая тайна"
- код "коммерческая тайна" списывается
- «живых» кодов на изделиях становится меньше
- следующие изделия тоже с нечитаемыми стикерами
- снова используется код "коммерческая тайна"
- …
```

**Эффект накапливается.** С каждой отгрузкой коды-сироты копятся: активны в системе, нечитаемы физически.

**Возврат соответствия:** Только полная инвентаризация с перемаркировкой всех изделий — что потребует значительных ресурсов.

**Рекомендация:** Частичная автоматизация в учётной системе + легализация схем работы.

---

## 4. Образование кодов-сирот

**Статус:** Высокая серьёзность

**Цепочка проблемы:**

1. Изделие на складе со стикером кода A.
2. В условиях хранения стикер повреждён → код A физически нечитаем, но в системе ещё активен.
3. При отгрузке персонал не может считать код A → используется "коммерческая тайна".
4. Код B уходит в реализацию, выводится из оборота. "коммерческая тайна".
5. Повторная печать старого стикера ограничена по времени, новый из перемаркировки клиент ждать не может.
6. Код A остаётся в системе активным, но:
   - стикер повреждён → нельзя отсканировать
   - изделие "комерческая тайна" → клиент сталкивается с несоответствием
   - если код A старше ограниченного периода → печатать повторно нельзя по правилам регулятора
   - если код A младше ограниченного периода → можно заказать перемаркировку, но "коммерческая тайна"
7. **Код A — сирота:** активен в системе, нечитаем физически, привязан к изделию, "коммерческая тайна".

**Рекомендация:** Внедрить процесс выявления и очистки кодов-сирот в процедуру инвентаризации.

## 5. Ограничения, блокирующие автоматизацию

**Статус:** Высокая серьёзность

**Суть противоречия:**

Попытка автоматизации процессов столкнулась с тремя слоями ограничений:

| Слой | Ограничение | Источник |
|-----|-------------|----------|
| **Хранение кодов** | Собственные полные коды у владельца должны быть удалены по истечении ограниченного периода, переходящие от поставщика вообще нельзя хранить | Правила регулятора |
| **Автоматическое подтягивание** | Автоматическое подтягивание кодов в накладную ограничено — их там не должно быть | Внутренние политики IT на основании правил регулятора |
| **Сканирование с изделий** | Единственный легальный путь, но физически затруднён: коды утрачиваются при складских операциях, "коммерческая тайна" | Физика склада |

**Рекомендация:** Комплексное решение — комбинация автоматизации в учётной системе + "коммерческая тайна" + изменение хранения для наиболее ходовых позиций.

---

## 6. Ограничение по сроку хранения кодов

**Статус:** Высокая серьёзность

**Правила регулятора вокруг кода:**

| Правило | Суть | Последствие для склада |
|---------|------|----------------------|
| **Код активен длительное время** | Пока статус «активный», код действителен | Изделие может использовать один код продолжительное время |
| **Печать стикера ограничена по времени** | С момента получения кода его можно распечатать на стикере в течение ограниченного периода | После истечения срока код существует только на стикере физически |
| **Хранение кодов ограничено** | Полные коды не должны находиться на стороне владельца по истечении ограниченного периода | Автоматическое подтягивание кодов в накладную ограничено |
| **Перемаркировка** | Можно заказывать повторно, каждая операция занимает время | Каждый раз — время на заказ и ожидание |
| **Период печати ~ 60 дней** | Свой код можно распечатать повторно только в течение ограниченного периода | Но наклеить нужно на конкретное изделие, с нечитаемым кодом, которое переходит клиенту |

**Рекомендация:** Автоматизация в учётной системе с контролем сроков + регулярная очистка кодов, превысивших ограниченный период хранения.

## 7. Рост нагрузки на персонал

**Статус:** Средняя серьёзность

**Изменение эффективности приёмки:**

| Период | Ответственные          | Сканирование | Время на партию | Изменения |
|--------|------------------------|--------------|-----------------|-----------|
| До внедрения маркировки | Грузчики               | Нет | Минимальное | — |
| После внедрения с узкой специализацией | Грузчики               | Каждое изделие | Увеличенное | Нечитаемые коды → перемаркировка → ожидание → товар недоступен |
| После оптимизации штата | Кладовщики             | Каждое изделие | Значительно увеличенное | Кладовщики одновременно обслуживает клиентов, время обработки варьируется |
| При договорах с поставщиками о кодах | Кладовщики | Коды из пакета документов | Умеренное | Только если поставщик передал коды |

**Оптимизация штата увеличила нагрузку:**
- Время приёмки выросло кратно
- Кладовщики одновременно выполняет функции приёмки и обслуживания клиентов
- Нагрузка не была перераспределена
- Функция выгрузки перешла Кладовщикам, клиентская нагрузка не снята

**Рекомендация:** Пересмотреть нагрузку персонала, рассмотреть возврат узкой специализации или доработку процесса приёмки.

## 8. Инвентаризация без полной сверки кодов

**Статус:** Средняя серьёзность

**Суть противоречия:**

- Инвентаризация проводится периодически, без ТСД — до кодов физически не добраться в стопках
- Внеплановые пересчёты проблемных позиций несколько раз в месяц
- Коды не сверяются полностью — сверка физически затруднена
- Инвентаризация контролирует только факт наличия продукции
- Данные могут быть неточными
- Реализованная продукция может физически находиться на складе с "коммерческая тайна"

**Рекомендация:** Внедрить адресное хранение для реализованной продукции + регулярную проверку соблюдения ограничений по срокам.

---

## 9. Риск «зависшей» продукции на внешних площадках

**Статус:** Средняя серьёзность

**Суть противоречия:**

В сценарии отгрузки на внешнюю площадку:
- Изделие может быть отгружено, но не забрано клиентом
- Статус товара будет неопределённым
- Это создаёт дополнительный тип расхождений, требующий дополнительных процессов

**Рекомендация:** "коммерческая тайна" + регламент обработки «зависших» изделий.

## Связь с предлагаемыми решениями

Выявленные противоречия напрямую влияют на выбор между вариантами решений из `solutions.md`:

### Вариант A — Легализация существующих схем
- **Решает:** противоречия 1, 9 (сценарии ответственного хранения и внешних площадок)
- **Плюс:** минимальные изменения процессов, которые уже работают
- **Минус:** требуется согласование с регулятором

### Вариант B — Частичная автоматизация в учётной системе
- **Решает:** противоречия 3, 4, 6 (деградация кодов, коды-сироты, ограничение по срокам)
- **Плюс:** ускорение отгрузки, сокращение ручного труда
- **Минус:** "коммерческая тайна"

### Вариант C — Изменение хранения
- **Решает:** противоречие 2 (разрушение стикеров)
- **Плюс:** коды доступны, сканирование с изделия физически возможно
- **Минус:** требуется увеличение площади хранения

### Вариант D — Гибрид (Комплексное решение)
- **Решает:** все противоречия
- **Подход:** B + A + частично C для ходовых позиций
- **Плюс:** снимает давление по всем направлениям
- **Минус:** требует комплексного решения, дополнительных затрат и согласования

## Выводы

1. **Корневая проблема** — конфликт между требованиями регулятора и физическими условиями хранения. Это системный конфликт требований, а не ошибка персонала.

2. **Фактически используемые сценарии** (ответственное хранение и отгрузка на внешние площадки) — перегружены противоречиями. Альтернативы, которая сохранила бы скорость отгрузки, нет.

3. **Автоматизация ограничена** на трёх уровнях: хранение кодов, автоматическое подтягивание в накладную, сканирование с изделий.

4. **Накопительный разрыв** между системой и реальностью растёт с каждой отгрузкой. Вернуть соответствие можно только полной инвентаризацией с перемаркировкой — что потребует значительных ресурсов.

5. **Рекомендуемый путь** — Вариант D (гибрид): частичная автоматизация в учётной системе + "коммерческая тайна" ответственного хранения и отгрузки на внешние площадки + изменение хранения для наиболее ходовых позиций.
