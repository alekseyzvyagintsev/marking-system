# Выявленные противоречия и способы их решения

## Обзор

В рамках анализа системы управления маркировкой грузовых шин выявлены критические противоречия между требованиями регулятора, физическими условиями склада и текущими бизнес-процессами.

**Ключевая проблема:** На складе одновременно действуют два взаимоисключающих требования. Их нельзя исполнить одновременно физически. Склад работает на «костылях», которые обеспечивают отгрузку, но нарушают требования регулятора.

---

## 1. Три взаимоисключающих сценария

**Статус:** Критическая серьёзность

**Суть противоречия:**

Существуют три сценария работы, которые по отдельности работают, но вместе создают неразрешимый конфликт:

### Сценарий 1 — требование «Честного знака» и руководства
- Каждое колесо сканируется с физического стикера при отгрузке
- Колесо уходит клиенту со стикером кода маркировки
- Код выводится из оборота в момент отгрузки
- Хранить полные коды на стороне владельца запрещено
- Стикер существует только на колесе, распечатать повторно — в течение 60 дней

### Сценарий 2 — реальность ответственного хранения (ОХ)
- Клиент не может ждать, пока поставщик даст коды, кладовщик отсканирует, а ЧЗ подтвердит
- Отгрузка идёт по счёту оплаты без реализации в 1С
- Реализация проводится постфактум, когда товар встанет на баланс
- Документы с кодами уходят клиенту по ЭДО позже

### Сценарий 3 — отгрузка в ночную смену на шиномонтаж
- Кладовщик работает ограниченное количество часов и не может ждать коды
- Отгрузка по счёту без реализации в 1С
- Клиент может установить шины и уехать — коды на шинах могут быть не актуальны
- Клиент может забрать шины с собой — коды не действительны
- Клиент может вообще не приехать — колесо остаётся на шиномонтаже в неопределённом статусе

**Почему сценарии несовместимы:**

| Требование | Сценарий 1 (ЧЗ) | Сценарий 2 (ОХ) | Сценарий 3 (шиномонтаж) |
|-----------|-----------------|-----------------|------------------------|
| Стикер на колесе | Колесо уезжает со стикером | Колесо уезжает без стикера | Колесо уезжает без стикера |
| Сканирование в момент отгрузки | Да | Отгрузка сейчас, оформление потом | Отгрузка сейчас, оформление потом, статус неизвестен |
| Код привязан к физическому колесу | Да | Код из документа в 1С | Код из документа в 1С |
| Хранить коды нельзя | Да | Быстрый доступ к кодам нужен | Быстрый доступ нужен + риск зависшего статуса |
| Вывод из оборота при отгрузке | Да | Вывод постфактум | Вывод постфактум, если клиент забрал товар |

**Сценарии 2 и 3 — самые нагруженные и единственные рабочие.** Они держатся на «костыле» отгрузки без реализации, который работает, но объявлен неправильным.

**Рекомендация:** Легализовать схемы ОХ и шиномонтажа через согласование с Честным знаком как допустимых схем для ответственного хранения.

## 2. Физическое разрушение стикеров при хранении

**Статус:** Критическая серьёзность

**Суть противоречия:**

Требование «сканировать с колеса и отдать со стикером» несовместимо с физическими условиями хранения шин в стопках.

**Почему стикеры разрушаются:**
- При постоянном ручном перекатывании и перекладывании стикеры трутся руками кладовщика
- Трение о соседние колёса в стопке (6–8 шт.)
- Трение об землю и пол при перекатывании
- Трение о борта и пол машины при погрузке/транспортировке/выгрузке
- Каждое касание — потенциал повреждения стикера
- Грузовая шина тяжёлая, контакт с поверхностью постоянный

**Сканирование с колёс:**
- Физически невозможно в стопках — это верно для инвентаризации с ТСД
- Именно поэтому ТСД при инвентаризации не используется
- Сканирование возможно только когда все колёса сняты со стопки И стикеры не нарушены

**Рекомендация:** Перейти на хранение накатом (не в стопках) для обеспечения доступа к стикерам, либо легализовать сканирование из документов 1С.

## 3. Замкнутый круг деградации кодов (накопительный эффект)

**Статус:** Критическая серьёзность

**Суть противоречия:**

С каждой отгрузкой разрыв между системой и реальностью растёт по замкнутому циклу:

```
Код нужен для отгрузки
→ на стикере он битый (из-за трения и стопок)
→ сканируем из «Приобретения» (запрещено, но работает)
→ код из «Приобретения» списывается
→ «живых» кодов на колёсах становится меньше
→ следующие колёса тоже с битыми стикерами
→ снова сканируем из «Приобретения»
→ …
```

**Круг не повторяется — он накапливает.** С каждой отгрузкой коды-сироты копятся: активны в системе, мертвы физически.

**Возврат соответствия:** Только полная инвентаризация с перемаркировкой всех колёс — что сделать невозможно или очень дорого.

**Рекомендация:** Частичная автоматизация в 1С (Вариант B) + легализация схем (Вариант A).

## 4. Цепочка образования кода-сироты

**Статус:** Высокая серьёзность

**Точная цепочка проблемы:**

1. Колесо на складе со стикером кода A.
2. В стопке/при перекатывании стикер повреждён → код A физически битый, но в системе ещё активный.
3. При отгрузке кладовщик не может считать код A → берёт код B из «Приобретения».
4. Код B уходит в реализацию, выводится из оборота. Колесо уезжает клиенту — без стикера кода B.
5. Старый распечатывать повторно запрещено правилами ЧЗ, новый из перемаркировки ждать клиент не хочет.
6. Код A остаётся в системе активным, но:
   - стикер битый → нельзя отсканировать
   - колесо уехало без стикера → клиент нервничает
   - если код A старше 60 дней → печатать повторно нельзя по правилам ЧЗ
   - если код A младше 60 дней → можно заказать перемаркировку, но наклеить некуда — колесо уехало
7. **Код A — сирота:** жив в системе, мёртв физически, привязан к колесу, которого нет.

**Рекомендация:** Внедрить процесс выявления и очистки кодов-сирот в процедуру инвентаризации.

## 5. Три слоя запрета, блокирующие автоматизацию

**Статус:** Высокая серьёзность

**Суть противоречия:**

Попытка автоматизации процессов провалилась из-за трёх слоёв запретов:

| Слой | Запрет | Источник |
|-----|--------|----------|
| **Хранение кодов** | Собственные полные коды у владельца быть не должны после 60 дней, переходящие от поставщика вообще нельзя | Правила ЧЗ |
| **Подтягивание в накладную** | Кнопка «Маркировка» не может брать коды из базы — их там быть не должно | IT на основании правил ЧЗ |
| **Сканирование с колёс** | Единственный легальный путь, но физически невозможен: коды утрачиваются при транспортировочных складских мероприятиях, массовая отгрузка без реализации | Физика склада |

**Реакция стейкхолдеров:**
- IT: «Не понимаю, зачем доработки. Заказывайте перемаркировку и продавайте.»
- Начальник направления → начальнику склада: «Почему плохо работаете?! Быстро исправить!»
- Как исправлять — не предложено.

**Рекомендация:** Комплексное решение (Вариант D) — комбинация автоматизации в 1С + легализация схем + изменение хранения для ходовых позиций.

## 6. Нарушение правила 60 дней

**Статус:** Высокая серьёзность

**Суть противоречия:**

Правила «Честного знака» вокруг кода:

| Правило | Суть | Последствие для склада |
|---------|------|----------------------|
| **Код активен бесконечно** | Пока статус «активный», код действителен | Колесо может ездить с одним кодом годами |
| **Печатать код можно 60 дней** | С момента получения кода его можно распечатать на стикере. Через ~60 дней код у владельца быть не должно | После 60 дней код существует только на стикере физически |
| **Хранить коды у себя нельзя** | Полные коды не должны находиться на стороне владельца после ~60 дней | Автоматическое подтягивание кодов в накладную запрещено |
| **Перемаркировка — бесконечная** | Можно заказывать сколько угодно раз, 50 копеек за код | Каждый раз — время на заказ, ожидание, затраты в расчет не берутся |
| **Заказанный код ~ 60 дней** | Свой код можем распечатать повторно только в течение ~60 дней | Но наклеить нужно на конкретное колесо, с битым кодом, которое переходит клиенту |

**Текущее состояние:** Использование кодов из «Приобретения» в 1С нарушает правило хранения — в теории кодов в «Приобретении» у склада быть не должно после 60 дней.

**Рекомендация:** Частичная автоматизация в 1С с условным хранением + регулярная очистка кодов старше 60 дней.

## 7. Деградация приёмки после увольнения грузчиков

**Статус:** Средняя серьёзность

**Суть противоречия:**

| Период | Кто выгружает | Сканирование | Время на 200 шт. | Что сломалось |
|--------|--------------|--------------|------------------|---------------|
| До маркировки | Грузчики | Нет | ~30 мин | — |
| Маркировка + грузчики | Грузчики | Каждое колесо ТСД | ~60 мин | Нечитаемые коды → перемаркировка → ожидание → товар недоступен |
| Грузчики уволены | Кладовщики | Каждое колесо ТСД | 60–180 мин | Кладовщики одновременно обслуживают клиентов, время плавает |
| Договоры с поставщиками о кодах | Кладовщики | Коды из пакета документов | 30–120 мин | Только если поставщик передал коды |

**Увольнение грузчиков усугубило проблему:**
- Время приёмки выросло в 3–6 раз
- Кладовщики одновременно выгружают и обслуживают клиентов
- Нагрузка не перераспределена
- Функция выгрузки перешла кладовщикам, клиентская нагрузка не снята
- На сканирование реализаций уходит до 2 часов в день

**Рекомендация:** Пересмотреть нагрузку кладовщиков, рассмотреть возврат грузчиков или доработку процесса приёмки.

---

## 8. Инвентаризация без сверки кодов

**Статус:** Средняя серьёзность

**Суть противоречия:**

- Инвентаризация раз в квартал, без ТСД — до кодов физически не добраться в стопках
- Внеплановые пересчёты проблемных позиций несколько раз в месяц
- Коды не сверяются — сверка физически невозможна
- Инвентаризация контролирует только факт наличия шин
- Данные неточные
- Проданные, но не принятые на ОХ шины физически лежат на складе — коды уже выведены из оборота = риск штрафа

**Рекомендация:** Внедрить адресное хранение для проданных шин + регулярную проверку 60-дневного правила.

---

## 9. Риск «зависших» колёс на шиномонтаже

**Статус:** Средняя серьёзность

**Суть противоречия:**

В сценарии шиномонтажа:
- Колесо может уехать, клиент не заберёт его
- Не отдал бумагу со склада на охрану
- Статус товара будет неопределённым
- Это новый тип расхождений, который ловится дополнительными процессами, отнимающими дополнительное время

**Рекомендация:** Легализация схемы постфактумной реализации + регламент обработки «зависших» колёс.

## Связь с предлагаемыми решениями

Выявленные противоречия напрямую влияют на выбор между вариантами решений из `solutions.md`:

### Вариант A — Легализация существующих схем
- **Решает:** противоречия 1, 9 (сценарии ОХ и шиномонтажа)
- **Плюс:** ничего не ломаем, процессы уже работают
- **Минус:** нужно согласование с ЧЗ, может не пройти

### Вариант B — Частичная автоматизация в 1С
- **Решает:** противоречия 3, 4, 6 (деградация кодов, коды-сироты, правило 60 дней)
- **Плюс:** ускоряет отгрузку, убирает до 2 часов ручного сканирования в день
- **Минус:** связь код–колесо остаётся условной, противоречит запрету на хранение

### Вариант C — Изменение хранения
- **Решает:** противоречие 2 (разрушение стикеров)
- **Плюс:** коды доступны, сканирование с колеса физически возможно
- **Минус:** накат занимает в 3–4 раза больше места, может не вписаться в склад

### Вариант D — Гибрид (Комплексное решение)
- **Решает:** все противоречия
- **Подход:** B + A + частично C для ходовых позиций
- **Плюс:** снимает давление по всем фронтам
- **Минус:** требует комплексного решения, доп. расходов и согласования

## Выводы

1. **Корневая проблема** — конфликт между требованиями регулятора и физическими условиями склада. Это не ошибка персонала, а системный конфликт требований.

2. **Единственные рабочие сценарии** (ОХ и шиномонтаж) — перегружены противоречиями и держатся на «костылях». Альтернативы, которая сохранит скорость отгрузки, нет.

3. **Автоматизация заблокирована** на трёх уровнях: хранение кодов, подтягивание в накладную, сканирование с колёс.

4. **Накопительный разрыв** между системой и реальностью растёт с каждой отгрузкой. Вернуть соответствие можно только полной инвентаризацией с перемаркировкой — что невозможно или очень дорого.

5. **Рекомендуемый путь** — Вариант D (гибрид): частичная автоматизация в 1С + легализация схем ОХ и шиномонтажа + изменение хранения для ходовых позиций.
